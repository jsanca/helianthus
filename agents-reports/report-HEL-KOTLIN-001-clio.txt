SUMMARY
-------
Produced an evidence-based architecture assessment of Helianthus to answer whether a
Ktor migration is justified, without modifying any production code. Read the full
backend (helianthus-core + helianthus-web), build config (Maven POMs, application.yml,
Dockerfiles, Paketo scripts), test suites, and the OSK docs (knowledge, ADR, phase
migration inventory, CRUD design).

Key findings: helianthus-core (~737 LOC) is already framework-independent (only
javax.sql.DataSource + SLF4J). ~60% of production LOC is framework-independent logic.
Spring's heavyweight features (transactions, async, scheduling, caching, JdbcTemplate,
ORM) are unused; the data layer is raw JDBC. The deepest Spring coupling is Spring
Security's Authentication type reaching three files (two permission evaluators + the
controller layer). Identified dead code (marshall package, QueryConfigBean/QueryParameterBean,
IncongruentColumnValueLengthException) and two test gaps (OperationPermissionEvaluator,
JSON serialization contract).

Recommendation: INVESTIGATE, gated by three spikes (blocking-JDBC-vs-coroutines model,
Keycloak JWT on ktor-server-auth-jwt, four-format responder stack). Gardening/characterization
work (HTTP golden fixtures, Principal/roles abstraction, dead-code removal) should begin
immediately regardless of the final decision.
